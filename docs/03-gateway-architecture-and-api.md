# สถาปัตยกรรม Station Gateway + API ระหว่าง Pi กับ UDOM Next

แยกระบบเป็นสองส่วนตามที่คุยกัน: **Raspberry Pi = ตัวกลางคุมฮาร์ดแวร์** กับ **UDCS = ระบบบัญชี/ขาย**
ต่อกันด้วย HTTP API ที่มี contract ชัดเจน ไม่ใช่ให้ agent ไปเรียก Supabase RPC ตรง ๆ แบบเดิม

---

## 1. ทำไมแยกแบบนี้ดีกว่า

| เหตุผล | ผล |
|---|---|
| แก้ฝั่งฮาร์ดแวร์ไม่ต้องแตะ UDCS | ถอดโปรโตคอลได้ใหม่ → deploy แค่ Pi |
| UDCS ไม่ต้องรู้จัก RS-485 | โดเมนสะอาด ทดสอบง่าย |
| ปั๊มสาขาอื่นใช้ซ้ำได้ | Pi เครื่องเดียวกัน เปลี่ยนแค่ config |
| เน็ตดับยังขายได้ | Pi มีฐานข้อมูลของตัวเอง ไม่พึ่งคลาวด์ตอนจ่ายน้ำมัน |
| เปลี่ยนปลายทางได้ | วันหน้าจะส่งเข้า ERP อื่นก็เขียน sink เพิ่ม |

## 2. ข้อจำกัดข้อเดียวที่กำหนดทุกอย่าง

```
Pi อยู่หลัง NAT ของปั๊ม (ไม่มี public IP, มักเป็น CGNAT ของ ISP)
  ⇒ UDCS ยิง HTTP เข้าหา Pi ไม่ได้
  ⇒ Pi ต้องเป็นฝ่ายเปิดการเชื่อมต่อออกไปเสมอ ทั้งขาขึ้นและขาลง
```

ทางเลือกที่พิจารณาแล้ว:

| วิธี | latency คำสั่ง | ความยุ่งยาก | สรุป |
|---|---|---|---|
| Pi poll ทุก 1 วิ | ~1 วิ | ต่ำสุด | ใช้เป็น fallback |
| **Pi long-poll (hold 25 วิ)** | **~0** | **ต่ำ** | ✅ **เลือกอันนี้** |
| WebSocket ค้าง | ~0 | กลาง | เกินจำเป็น |
| Cloudflare Tunnel / Tailscale | ~0 | สูง (ต้องดูแล tunnel) | ไว้ทีหลังถ้าต้องเข้า UI ของ Pi จากนอก |

**long-poll** = Pi ยิง GET แล้วเซิร์ฟเวอร์ "ค้างสาย" ไว้ 25 วินาที ถ้ามีคำสั่งก็ตอบทันที
ไม่มีก็ตอบว่างเปล่าแล้ว Pi ยิงใหม่ → ได้ latency เท่า WebSocket แต่เป็น HTTP ธรรมดา ผ่าน NAT/proxy ได้หมด

## 4. Raspberry Pi ไหวไหม — คำนวณจริง

### 4.1 คอขวดอยู่ที่ RS-485 ไม่ใช่ Pi

ที่ 9600 baud 8N1 → 10 บิต/ไบต์ → **1.042 ms ต่อไบต์**

```
1 exchange = ถาม 6 B (6.3 ms) + บอร์ดคิด (~10 ms) + ตอบ 8 B (8.3 ms) + เว้นช่วง (20 ms)
           ≈ 45 ms   ⇒ เพดาน ~22 exchange/วินาที ต่อหนึ่งบัส
```

| รูปแบบการ poll | เวลาต่อรอบ (4 บอร์ด) | ใช้บัส |
|---|---|---|
| ทุก 200 ms | 190 ms | **95% ← ชนเพดาน** |
| ทุก 500 ms | 190 ms | 38% ✅ |
| **adaptive: ว่าง 1000 ms / กำลังจ่าย 250 ms** | — | **~37%** ✅ ตอบสนองดีกว่า |

> **ข้อสรุป: ตั้ง poll ถี่กว่า 250 ms ไม่ได้ช่วยอะไร เพราะสายเต็มก่อน**
> ถ้าบอร์ดตั้ง 19200 baud ได้ เพดานจะเพิ่มเท่าตัว

### 4.2 ทรัพยากรบน Pi

| รายการ | ใช้จริง | Pi 4 2GB |
|---|---|---|
| CPU | ~32 เฟรม/วิ × 20 ไบต์ | <2% |
| RAM | Node ~70 MB | 3.5% |
| เขียนดิสก์ | ~3,000 แถว/วัน (totalizer 8×288 + รายการขาย) | ไม่มีนัย |
| เน็ตขาขึ้น | ~3 MB/วัน = 90 MB/เดือน | ไม่มีนัย |

**Pi 3B+ ก็ยังไหว — Pi 4 2GB คือจุดพอดี ไม่ต้องถึง Pi 5**
และเครื่องเดียวรับงาน ATG (Modbus 4 probe ทุก 10 วิ) เพิ่มได้สบาย

### 4.3 ฮาร์ดแวร์ที่ควรเลือก (สำคัญกว่ารุ่นของ Pi)

| ต้องมี | เหตุผล |
|---|---|
| **บูตจาก SSD/USB หรือ eMMC ห้าม SD card** | SD card ตายเพราะ log เขียนทั้งวัน = สาเหตุอันดับ 1 ที่ Pi หน้างานพัง |
| **RTC module (DS3231)** | Pi ไม่มีนาฬิกาในตัว ไฟดับ+เน็ตดับ → timestamp เพี้ยน → กะและการกระทบยอดพัง |
| **UPS / DC-UPS** | ไฟตกบ่อย และตัดกลางการเขียนดิสก์ |
| hardware watchdog (BCM2835) + `WatchdogSec` ใน systemd | ค้างแล้วต้องรีบูตเอง ไม่ต้องรอคนไปกด |
| เคสโลหะไม่มีพัดลม + อยู่ในห้องสำนักงาน | ห้ามอยู่ในรัศมี Zone ของตู้จ่าย |
| 4G สำรอง | เน็ตปั๊มล่มบ่อย |
| `log2ram` หรือ rootfs read-only + overlayfs | ลดการเขียนดิสก์ |

## 5. API Contract

Base: `https://<udcs-domain>/api/v1/station`

### 5.1 ความปลอดภัย

ทุก request จาก gateway ต้องมี:

```http
Authorization: Bearer <device_token>       # ASCII เท่านั้น (HTTP header รับได้แค่ ASCII)
X-Gateway-Id:  pi-forecourt
X-Station-Id:  STN-001
X-Timestamp:   2026-09-16T10:22:31.000Z    # ต้องอยู่ใน ±5 นาที
X-Nonce:       <uuid>                      # ห้ามซ้ำ (กัน replay)
X-Signature:   <hex>
```

```
X-Signature = HMAC-SHA256(device_secret,
    timestamp + "\n" + nonce + "\n" + method + "\n" + request_target + "\n" + sha256(body))
```

> ⚠️ `request_target` ต้องเป็น **path + query string เต็ม** และทั้งสองฝั่งต้องใช้ค่าเดียวกัน
> (ถ้าฝั่งหนึ่งใช้ path เปล่า GET ที่มี query จะลายเซ็นไม่ตรงตลอดกาล — เจอมาแล้วตอนทดสอบ)
>
> ⚠️ `device_token` และ `station_id` ต้องเป็น ASCII ล้วน
> ถ้าใส่อักขระไทย `fetch` จะล้มเหลวทุกครั้งและ gateway จะออฟไลน์เงียบ ๆ โดยไม่มีใครรู้สาเหตุ
> (โค้ดใน `sink/udcs.js` ตรวจให้ตั้งแต่ตอนเริ่มแล้ว)

### 5.2 ขาขึ้น — `POST /packages`

```jsonc
{
  "package_id": "uuid",
  "station_id": "STN-001",
  "gateway_id": "pi-forecourt",
  "sent_at": "2026-09-16T10:22:31.000Z",
  "queue_depth": 3,                        // ให้ UDCS เห็นว่าหน้างานมีของค้างแค่ไหน
  "events": [
    { "event_id": "uuid", "type": "pump.transaction",
      "occurred_at": "2026-09-16T10:21:02.000Z", "data": { /* ... */ } }
  ]
}
```

ตอบกลับ:
```jsonc
{
  "accepted": ["uuid", "uuid"],            // gateway ลบออกจากคิวได้
  "rejected": [{ "event_id": "uuid", "reason": "ข้อมูลผิดรูป" }],   // ทิ้งถาวร
  "server_time": "2026-09-16T10:22:31.200Z",
  "commands": [ /* แนบคำสั่งกลับมาได้ เผื่อ long-poll หลุด */ ]
}
```

**ACK ทีละ `event_id` ไม่ใช่ทั้งชุด** — ชุดหนึ่งมี 200 เหตุการณ์ ถ้า 1 อันผิดรูป อีก 199 ต้องผ่านได้

### 5.3 ขาลง — `GET /commands?gateway_id=..&wait=25`

เซิร์ฟเวอร์ค้างสายไว้ถึง 25 วินาที ตอบทันทีเมื่อมีคำสั่ง

```jsonc
{ "commands": [
  { "id": 4471,
    "ticket_ref": "uuid",                  // ⚠️ ใช้ตัวนี้กันคำสั่งซ้ำ ไม่ใช่ id
    "kind": "AUTHORIZE_AMOUNT",
    "nozzle_code": "gas95_front",
    "payload": { "amount": 500 },
    "expires_at": "2026-09-16T10:23:31.000Z" }
] }
```

> ⚠️ **กันซ้ำด้วย `ticket_ref` (uuid) ห้ามใช้ `id`**
> `id` เป็นเลขรันนิ่งของฐานข้อมูล ถ้าย้าย instance หรือ restore ฐานข้อมูลแล้วเลขวนกลับ
> คำสั่งจริงจะถูกทิ้งเพราะนึกว่าซ้ำ — เคสนี้โผล่มาจริงตอนทดสอบ

**ผลของคำสั่งส่งกลับทางขาขึ้น** เป็น event `command.result` ไม่ต้องมี endpoint แยก

### 5.4 ชนิดเหตุการณ์

| type | ถาวร? | หมายเหตุ |
|---|---|---|
| `pump.transaction` | ✅ **ห้ามหายเด็ดขาด** | รายการขาย |
| `pump.totalizer` | ✅ | ยอดสะสม ใช้กระทบยอด |
| `pump.alarm` | ✅ | |
| `command.result` | ✅ | DONE / ERROR / EXPIRED |
| `tank.reading`, `tank.delivery` | ✅ | เฟส ATG |
| `pump.live` | ❌ **ห้ามลงคิว** | สถานะสด |

**การแยกนี้สำคัญมาก:** สถานะสดของเมื่อ 3 ชั่วโมงที่แล้วไม่มีประโยชน์
ถ้าเอาลงคิวด้วย เน็ตดับ 1 คืนจะได้คิวหลักแสนแถวที่ไม่มีค่า แล้วรายการขายจริงจะถูกดันตกท้ายแถว

## 6. พฤติกรรมตอนเน็ตดับ (ทดสอบแล้ว)

```
เน็ตดี    → เหตุการณ์ถาวรลง SQLite → ส่งขึ้นทุก 1 วิ → ปลายทาง ACK → ลบออกจากคิว
เน็ตดับ   → ยังขายได้ปกติ เหตุการณ์ถาวรค้างในคิว สถานะสดถูกทิ้ง (ไม่สะสม)
          → retry แบบ exponential backoff 1→2→4→…→60 วิ
เน็ตกลับ  → ส่งของค้างขึ้นเองตามลำดับ ไม่ต้องสั่ง → คิวว่าง
คิวล้น    → ทิ้งของเก่าที่ "ไม่ใช่รายการขาย" ก่อนเสมอ รายการขายไม่ทิ้ง เตือนแทน
```

กันซ้ำสองชั้น: gateway ส่งซ้ำได้ (at-least-once) + ปลายทาง dedupe ด้วย `event_id`
→ ส่งซ้ำกี่ครั้งก็ได้ข้อมูลชุดเดียว

## 7. UI สำรองใน LAN (แนะนำ เฟส 2)

ถ้าเน็ตดับ PWA บนคลาวด์จะใช้ไม่ได้ **แต่ปั๊มต้องขายต่อได้**
→ ให้ Pi เสิร์ฟหน้าเว็บง่าย ๆ ใน LAN (`http://pi.local:8080`) สำหรับสั่งจ่าย + ดูยอด

> **ข้อจำกัดที่ต้องรู้:** PWA ของ UDCS เป็น HTTPS บน Cloudflare
> จะให้มันยิงตรงหา `http://192.168.x.x` ของ Pi **ไม่ได้** เพราะ browser บล็อก mixed content
> ทางออกคือ **แยกเป็นคนละหน้าเว็บ** — เปิด `http://pi.local:8080` ตรง ๆ (http ทั้งหน้า = ไม่ติด mixed content)
> ถ้าอยากให้ PWA คุย LAN ตรงจริง ๆ ต้องมี cert จริงให้ Pi (Tailscale / cloudflared / DNS-01)

## 9. สิ่งที่ UDCS ต้องทำ (ตอนพร้อม — ยังไม่ต้องทำตอนนี้)

1. ตาราง `station_gateways (gateway_id, station_id, device_token_hash, device_secret, last_seen_at)`
2. Edge Function หรือ Worker 2 เส้นทาง: `POST /packages`, `GET /commands`
   (long-poll บน Cloudflare Workers ใช้ได้ แต่ถ้าติดข้อจำกัดเวลา ให้ลด `wait` เหลือ 20 วิ)
3. ตัว handler แปลง event → ตารางตาม `sql/2026-09-15_pump_agent.sql`
4. ฝั่ง PWA: `request_pump_command` → insert `pump_commands` → gateway รับไปทำ
5. **ห้ามให้ปุ่มสั่งจ่ายผ่าน `js/offline_outbox.js`** — ออฟไลน์ = ปุ่มต้องเทา

## 10. คำถามที่ยังค้าง

1. UDCS จะรับ API ที่ไหน — Cloudflare Worker (มีอยู่แล้ว) หรือ Supabase Edge Function
   → Worker น่าจะดีกว่าเพราะ long-poll ถือ connection ได้ และคุณมี `wrangler.jsonc` อยู่แล้ว
2. หนึ่ง Pi ต่อหนึ่งสาขา หรือจะขยายหลายสาขาในอนาคต (มีผลกับ `station_id` และการออก token)
3. จะให้ Pi ทำ ATG ด้วยในเครื่องเดียวกันเลยไหม (ทรัพยากรเหลือเฟือ แนะนำว่าใช่)
